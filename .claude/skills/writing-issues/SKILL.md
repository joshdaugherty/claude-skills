# Writing Issues

Adapted from `uams-statamic`'s `writing-issues`. **The craft ported; the machinery did not.**
This repo has **no project board, no iterations, no milestones, no `afk`/`hitl` execution mode
and no epics** — measured, not assumed — so the whole GraphQL board-filing section of the
source skill is deliberately absent. What it does have is a much sharper evidence standard,
because its product is a diagnostic tool and a wrong issue here becomes a wrong diagnosis.

---

## ⛔⛔ THE RULE THIS REPO ADDS: MEASURE THE SPECIFIC CLAIM BEFORE YOU FILE IT

# **An issue asserting a defect must quote the command and the output that shows it.**

*Not the code that implies it. Not a rule the code appears to violate.* **The observed failure.**

⚠ **This is not theoretical — it is the most recent lesson this repo has.** On 2 Sep 2026 a
session filed an issue claiming `Number(m.ts)` could misorder Slack timestamps, on the strength
of a genuine rule in `SKILL.md:574` about float coercion. **The rule is real. The application of
it was wrong**, and one measurement would have shown it:

```
round-trip String(Number(ts))        LOSSLESS
ulp near 1.788e9                     2.38e-7 s
Slack ts granularity                 1e-6 s      ← 4x the ulp
ordering breaks above ts ~ 4.5e9 s   the year 2112
```

The issue was withdrawn and closed as not-a-defect within the hour. **A conclusion inherited
from an adjacent true statement is the failure mode this rule exists to stop.**

So, before filing:

| **Run it.** | *A defect you have not watched happen is a hypothesis. File it as one, in those words.* |
| :-- | --- |
| **Quote real output.** | *Paste what the terminal printed, not what you expect it to print. Reading the code does not tell you what the tool says.* |
| **Cite lines you have opened.** | ⚠ *An issue on 2 Sep cited `poll()` returning true for `ratelimited` **at a line number that has no such branch** — the behaviour claim was right, the citation was invented. Open the file.* |
| **Say "unverified" when it is.** | *"Reasoned from the API contract; nobody here has observed a 429" is a **useful** issue. A confident one that turns out wrong costs a retraction.* |

★ **Bounded negatives are findings.** *"Checked all 13 push sites; zero begin with `ASK`"* is
worth as much as a hit, and it stops the next reader repeating the search.

## The disclaimer rule (non-negotiable)

**Never** add a `> *This was generated by AI during triage.*` blockquote, or any equivalent
"written by AI" line, to an issue body. Do not replicate it; strip it when rewriting.

## Titles

Imperative, verb-first, naming the deliverable or the outcome — what the issue *accomplishes*,
not a topic label. **No trailing period.**

- **Default — imperative outcome:** ``Stop `--doctor` reporting a verdict its inputs cannot support``,
  ``Route timestamp comparisons through an exact `tsCmp()` ``
- **Bugs may lead with the symptom**, naming the component and the user-visible consequence:
  ``` `--consistency` reports "Every registration matches the newest cached version" when there is no cached version ```,
  ``` `--raw --since` filters messages, then reports the unfiltered count ```
- **Backtick anything a developer would type or grep** — flags (`--doctor`, `--heartbeat`),
  functions (`caseDuplicateRegistrations()`), files (`slack-watch.mjs`), env vars
  (`SLACK_BOT_TOKEN`), API methods (`chat.update`).
- **Disambiguating parenthetical** when it sharpens: `(in two string literals)`,
  `(the escalation never fires)`.
- ⛔ **No Conventional-Commit prefixes.** `feat:` / `fix:` / `chore:` belong on commits.

**A title may state the count when the count is the finding** — ``The documented "complete set"
of Slack endpoints is four; the scripts call six`` — because the number *is* the defect.

## Body: the standard skeleton

Drop what does not apply; **never drop `## Acceptance criteria`** on a work item, and never drop
the measurement on a defect report.

1. **Lede** — 1–3 sentences. The user-visible effect or the mechanism, not the implementation.
   May open with a **provenance line**: `Found while fixing #102.`, `Follow-up to #80.`,
   `Raised by three of the six review lenses.` Provenance says where it came from; it never
   states a dependency.
2. **`## The mechanism`** — quote the offending code in a fenced block and walk it.
3. **`## Measured`** — the command and its real output. *This is the section this repo adds.*
4. **`## Why it matters`** — the concrete failure: who runs what, and what they are told.
5. **`## Fix`** / **`## Proposed fix`** — the recommended path, and the design decision behind it.
6. **`## Acceptance criteria`** — a task list of observable outcomes.
7. **`## Out of scope`** — non-goals, each pointing at its tracking issue.
8. **`## References`** — files, sibling issues, external docs.

## Section inventory

Use the established names; don't invent synonyms casually.

- **`## The mechanism`** — how the defect works, with the code quoted.
- **`## Measured`** / **`## Reproduce`** — the commands and their output. Include the
  **fixture** if one was built (a fabricated `HOME`, an orphaned cache dir).
- **`## Why it matters`** — the operator's or peer session's experience of it.
- **`## Why no lens found it`** — when triage itself has a gap worth recording.
- **`## Fix`** / **`## Proposed fix`** — including what was deliberately *not* done, and why.
- **`## Out of scope`** · **`## References`** · **`## Notes`**
- ⛔ **`## Not reachable from here`** — **this repo's own section.** When a claim cannot be
  verified by any agent — mrkdwn rendering on a human's screen, macOS `launchd` behaviour,
  whether a skill invocation resolves — **name the observer required** and say the claim is
  unverified. See [`adversarial-review`](../../rules/adversarial-review.md), which calls this
  the third defect tier.

## Acceptance criteria

- A GitHub **task list** (`- [ ]`), one box per independently verifiable outcome.
- Each item is an **observable outcome**, not an implementation step.
- **Bound the behaviour on both sides** — assert the new behaviour *and* that the unaffected
  cases still hold. *"`--consistency` prints `?` with no cache; the same rows WITH a cache still
  print `ok`/`BEHIND`."*
- **End with a verification item**, and in this repo that means a **negative control**:
  reintroduce the exact defect and confirm the suite goes red *for the right reason*.
  *"Reintroducing the defect fails exactly the three new fixtures and no others."*
- ⚠ **A test whose expected value was copied from the output is not a test.** The expectation
  must come from somewhere the implementation cannot reach.

## Dependencies belong in the edges, never in the body

**Never write `Blocked by #N.` or `Blocks #N` into an issue body.** Use GitHub's native
dependency edges. Prose and edges drift apart, and **the prose is the half that fails silently**
— the edge is machine-maintained, the sentence is not.

**The carve-out — context cross-references stay**, because the graph does not track them:

- **Provenance** — `Found while fixing #102.`, `Follow-up to #80.`, `Spun off from #47.`
- **Inline cross-refs** — `tracked in #N`, `see #105 / #106`.
- **Naming what something is** — "the shape #91 fixed, one command over".

Where a body must explain why something waits, describe the **condition** — what has to be true
— rather than naming a ticket as the gate.

⚠ **Qualify every cross-repo reference** (`Org/Repo#N`). A bare `#N` resolves against the
repository the body lives in.

## Inline code, links, bullets

- **Backtick aggressively**: flags, file paths, function names, env vars, API methods, version
  arrows (`` `2.19.2` → `2.20.0` ``), and any string being compared (`` `HART` vs `HUNT` ``).
- **File paths are linked** to the absolute branch URL —
  `` [`slack-watch.mjs`](https://github.com/joshdaugherty/claude-skills/blob/main/plugins/slack-as-claude/skills/slack-session-bus/slack-watch.mjs) ``.
- **Fenced blocks** (`js`, `bash`, `text`) quote the offending code and the real output. Show
  before/after as two labelled blocks, not a `diff` block.
- **Bullets are `-` only**, 2-space nesting. **Bold-tag lead-ins** categorize; **em-dash `—`**
  separates tag from prose.
- **Tables** for naturally tabular data — site inventories, before/after counts, lens coverage.

## Labels

The repo carries the **default GitHub label set**. All three of `bug`, `documentation` and
`enhancement` see real, regular use - MEASURED just now: `gh issue list --state all` shows
`bug` and `documentation` both used dozens of times, not one dominant label with the others
as noise. Re-measure before citing a count here; it is a claim about the world, not this file.

# ⚠ **APPLY THE LABEL. A SESSION FILED TWENTY ISSUES ON 2 SEP 2026 AND LABELLED NONE OF THEM**,
against a 34-issue precedent, because `gh issue create` succeeds happily without one.

```bash
gh issue create --repo joshdaugherty/claude-skills --label bug --title '…' --body-file …
```

Use `bug` for a defect, `enhancement` for new behaviour, `documentation` for a docs-only fix.
⚠ **In this repo a `SKILL.md` defect is a `bug`, not `documentation`** — the instructions *are*
the behaviour.

## Check for an existing issue first

Search the tracker for one covering the same **concept** — match on the idea, not the title —
and **include closed issues**. A withdrawn issue is a strong signal: it may mean the claim was
already measured and refuted.

```bash
gh issue list --repo joshdaugherty/claude-skills --state all --search '<symptom>'
gh issue list --repo joshdaugherty/claude-skills --state all --search '<flag or function>'
gh issue list --repo joshdaugherty/claude-skills --state all --search '<defect class>'
```

⚠ **And check the closed ones for a withdrawal before re-filing the same reasoning.** `#110` was
closed as not-a-defect *with the measurements attached*; refiling it would repeat a settled
question.

## ⛔ When consolidating findings, count them out as well as in

**A review that produces 47 findings and 19 issues has dropped 28 somewhere.** On 2 Sep 2026 a
finding raised independently by **three** lenses — `--consistency` demanding a `--channel` it
never uses — vanished in exactly that step and had to be filed late as `#112`.

**List every finding, mark each one filed / merged-into-#N / rejected-because, and say which.**
A silent drop reads identically to a decision.

## The archetypes this repo actually produces

Its defects cluster, and naming the cluster in the lede helps the reader instantly:

| **A surface reporting what its state cannot support** | *A null guard skips the comparison, and the summary reports the absence of one as a pass.* `#88` `#89` `#90` |
| :-- | --- |
| **A fix that landed where it was reported and nowhere else** | *The same constant, guard or instruction in N copies; one gets fixed.* `--heartbeat` was wrong in **four** string literals across three releases. `#79` `#93` `#94` `#95` |
| **A documented path that does not run as written** | *A SKILL.md edit is a code change here.* `#92` `#98` `#100` |
| **A guard that has never fired has never been read** | *A TDZ crash in the branch that only runs when the diagnostic has something to report.* |
| **A stored conclusion about the world, ageing silently** | *"Only one registration is reachable" — true when written, false within the hour.* **Emit the observation, not the conclusion.** |
| **An outside-observer defect** | *mrkdwn on a human's screen, macOS `launchd`.* **No agent can reach it — name the observer.** |
| **A withdrawal** | *A previous claim, measured and retracted. Banner the correction and keep the text — the past does not move.* `#110` |

## Tone and voice

- Technical, prose-driven, specific. Lead with *why*, then *what*. Concrete flags, paths,
  commands and error strings over generalities.
- Bound scope deliberately — `## Out of scope` is part of writing a good issue.
- **No emoji in prose, no exclamation marks.** The `⛔ ⚠ ★ ✔` markers are structural, used at
  the head of a claim to signal its weight, and are house style here — not decoration.
- **Impersonal voice.** Every artifact posts under one account: no `I` / `my` / `you` / `your`,
  and no vouching stance. **Report what was measured, not who measured it.**
- **Write the correction into the artifact that carried the error**, rather than editing it
  away. This repo has withdrawn several of its own readings; that is the process working.

## Example shape

**Title:** `` `--consistency` reports "Every registration matches the newest cached version" when there is no cached version ``

````markdown
Found while reviewing the verdict paths for #88 — the same shape, one command over.

## The mechanism

`slack-watch.mjs`, inside the `--consistency` version-comparison loop (at the time of #89 -
this example is illustrative, not a live citation; re-derive the line before quoting one):

```js
const behind = newest && cmpVer(r.version, newest) < 0;
```

When the cache walk found nothing, `newest` is `null`, so `behind` is `null` for **every** row.
`problems` never increments and the clean-bill branch a few lines below is taken.

## Measured

Hand-built home: two registrations, no cache directory.

```
cache: 0 version directories, newest non-orphaned none
  ok     2.19.2   user     (user)
  ok     2.0.0    project  D:\repo-one
Every registration matches the newest cached version, and no directory is registered twice.
EXIT=0
```

The two rows are **19 minor versions apart** and both read `ok`.

## Why it matters

The stated purpose is "is this MACHINE consistent". An operator auditing a machine whose cache
was pruned is told every registration matches, and exits 0.

⚠ The mirror guard sits **eleven lines above**, for the other empty input: `if (!reg.length)`
prints "That is NOT a clean bill of health". The shape was known and written once.

## Acceptance criteria

- [ ] With no non-orphaned cache directory, every row prints `?` and not `ok`
- [ ] The summary says nothing was compared, rather than reporting a pass
- [ ] With a cache present, the same rows still print `ok` / `BEHIND` (the control)
- [ ] The duplicate-directory check still runs and reports, since it needs no cache
````
